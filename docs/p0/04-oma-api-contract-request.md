# Запрос API-контрактов ОМА

Статус: **внешний блокер**. Публичные production-контракты ОМА в репозитории отсутствуют. Имена ниже — требуемые возможности, а не утверждение о существовании конкретных endpoint.

## Что запросить

Для каждого API нужны OpenAPI 3.1/JSON Schema, sandbox, тестовые данные, владелец, политика версий, лимиты, timeout/retry-рекомендации, SLA и канал инцидентов.

### 1. Авторизация и профиль

- OIDC discovery URL, issuer, audience, JWKS и поддерживаемые flows;
- claims: стабильный `sub`, tenant/brand, регион, роли/scopes;
- TTL access/refresh token, отзыв, logout, MFA для административных ролей;
- правила связи анонимной корзины с вошедшим пользователем;
- запрет PII в токенах сверх необходимого минимума.

Минимальные scopes: `catalog.read`, `price.read`, `stock.read`, `cart.read`, `cart.write`, `project.read`, `project.write`; административные scopes отделены.

### 2. Каталог

Нужны поиск и пакетное чтение по SKU. Минимальная модель товара:

```json
{
  "sku": "string",
  "name": "string",
  "status": "active|inactive",
  "categoryId": "string",
  "brand": "string",
  "unit": "piece|pack|m|m2|l|kg",
  "packSize": 1,
  "attributes": {},
  "media": [{"url": "https://...", "alt": "string"}],
  "updatedAt": "date-time",
  "version": "string"
}
```

Нужно отдельно подтвердить права на использование названий, описаний, характеристик и изображений в OMA ONE.

### 3. Цена

Пакетный запрос по SKU, региону/магазину, каналу и, если применимо, сегменту клиента. Ответ должен содержать:

- валюту и цену с налогами;
- обычную и акционную цену;
- основание/тип акции и период действия;
- единицу цены и размер упаковки;
- `observedAt`, `validUntil`, `version`;
- признак, является ли цена окончательной для корзины.

Итог всегда пересчитывает коммерческий контур ОМА. OMA ONE не принимает цену или скидку из браузера.

### 4. Остаток и доступность

Пакетный запрос по SKU и месту исполнения:

```json
{
  "sku": "string",
  "locationId": "string",
  "status": "in_stock|low_stock|out_of_stock|unknown",
  "availableToPromise": 0,
  "unit": "piece",
  "observedAt": "date-time",
  "version": "string"
}
```

Нужно определить семантику `availableToPromise`, допустимость показа точного количества, задержку обновления и поведение при частичном наличии. Если резервирование выполняет корзина/checkout ОМА, OMA ONE не создаёт параллельный резерв.

### 5. Корзина

Нужны операции получения корзины и серверного добавления набора позиций. Обязательные свойства:

- идентификация корзины из серверной сессии, не произвольным `userId`;
- `Idempotency-Key` для мутаций;
- optimistic concurrency (`version`/ETag);
- частичный успех либо атомарность набора — выбрать и документировать;
- фактически принятые количества, отклонённые позиции и причины;
- итоговые цены/скидки только из ответа ОМА;
- ссылка/deep link на продолжение оформления.

### 6. Заказ, доставка и возврат

В первом MVP OMA ONE не создаёт заказ. Нужны только согласованный переход в существующее оформление и, при необходимости, read-only статус заказа. До расширения scope запросить отдельные контракты заказа, оплаты, доставки, отмены и возврата.

### 7. Мастера и услуги

Нужны контракты каталога услуг, зон обслуживания, расписания, тарифов, создания/отмены брони и статусов работы. Мутации брони должны иметь idempotency key и version; контакты клиента выдаются только назначенному мастеру.

### 8. SyncCity

Нужны операции создания, поиска, вступления, выхода и закрытия группы; правила порога, скидки, отмены и пересчёта. Публичный ответ не содержит точных адресов, имён, телефонов и идентификаторов других участников.

### 9. Proof, OMA DNA и объектное хранилище

Нужны signed upload, проверка MIME/magic bytes, ограничения размера, удаление EXIF, antivirus/content scan, карантин, статусы модерации, приватность, публикация, отзыв и удаление. DNA возвращает только обезличенные одобренные проекты с версией правил.

### 10. OMA FORGE и OMA PULSE

FORGE требует идемпотентного голоса/отзыва, версий состава, статусов ручного утверждения и отделения интереса от заказа. PULSE требует приёма сигнала, дедупликации, экспертного решения, аудита, подписки/отписки и доставки уведомления.

### 11. Внешний AI-провайдер

Нужен серверный adapter contract: модель, таймаут, лимиты, политика хранения, регион обработки, субподрядчики, safety categories и детерминированный fallback. Модель не получает токены, секреты, фото или персональные данные без явно утверждённого потока.

## Единая ошибка

Согласовать машинный код, безопасный текст и correlation id, например:

```json
{
  "error": {
    "code": "STOCK_CHANGED",
    "message": "Доступность изменилась",
    "correlationId": "string",
    "retryable": true,
    "details": []
  }
}
```

Минимально различать `INVALID_ARGUMENT`, `UNAUTHENTICATED`, `FORBIDDEN`, `NOT_FOUND`, `PRICE_CHANGED`, `STOCK_CHANGED`, `VERSION_CONFLICT`, `RATE_LIMITED`, `UPSTREAM_UNAVAILABLE`.

## Сквозные требования

- TLS, способ сервисной аутентификации и ротация ключей;
- correlation/trace id, формат времени UTC ISO 8601, локаль и BYN;
- лимиты пакетных запросов и rate limit headers;
- правила кэширования и запрет кэша для персональных ответов;
- идемпотентность и дедупликация;
- пагинация и стабильная сортировка;
- webhooks/события обновления, если доступны;
- совместимость версий, deprecation window и changelog;
- перечень персональных данных и границы журналирования;
- нагрузочный профиль и окна обслуживания.

## Критерии готовности контракта

Контракт считается полученным, когда:

1. схема проходит валидацию и покрывает все обязательные операции;
2. для каждого поля описаны источник, единица, nullable/required и семантика;
3. есть примеры success, empty, partial, conflict и unavailable;
4. sandbox воспроизводит изменение цены/остатка и повтор мутации;
5. известны владелец, SLA, лимиты и канал инцидентов;
6. выполнен consumer-driven contract test из CI;
7. письменно зафиксировано, какая система является source of truth.

## Разрыв с текущим демо

| Демо сейчас | Production-требование |
|---|---|
| Каталог, цена и остаток из `seed.ts` | Только данные и версии из API ОМА |
| `userId` передаёт браузер | Пользователь определяется серверной SSO-сессией |
| Локальная JSON-корзина | Корзина ОМА с idempotency и concurrency control |
| Локальный «демо-заказ» | Переход в существующий checkout ОМА |
| Клиент присылает рассчитанный `plan` обратно | Сервер пересчитывает по SKU и версии правил |
| Неописанные ошибки | Версионированный error contract |
| Нет sandbox/contract tests | Sandbox и тесты поставщика/потребителя |

## Вопросы владельцам ОМА

1. Какой канал является целевым: web, WebView, SDK или backend-to-backend?
2. Есть ли единый SKU во всех регионах и как кодируется упаковка?
3. Цена зависит от магазина, способа получения, карты лояльности или клиента?
4. Остаток означает физическое количество или доступное к обещанию?
5. Кто выполняет резерв и на каком шаге?
6. Поддерживает ли корзина атомарное добавление комплекта и альтернативы?
7. Как вернуть пользователя в исходный проект после checkout?
8. Какие данные можно хранить в OMA ONE и какой срок?
9. Какие требования ИБ и нагрузочные лимиты обязательны для пилота?
10. Кто подписывает контракт и уведомляет о несовместимых изменениях?
